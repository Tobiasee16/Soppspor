# Marked routes, as vector geometry

Generated by `scripts/fetch_trails.py`. Not a model input.

## Why vector and not tiles

A tile server draws a route line about two pixels wide, so its apparent thickness is fixed at fetch time and scales with the tile's resolution rather than with the map. At the deepest zoom the embedded 9 m/px sheet turned a footpath into a band roughly 120 screen pixels across, which is not a path but a claim that the path is somewhere in there.

The suitability zones never had this problem because they are traced as vector paths and stroked at a width measured in screen pixels. Routes are now the same kind of object: sharp at every zoom, thickness set by one number in the interface, and no network needed to draw them.

## Checks

The WFS is asked for EPSG:25833 and answers easting-first. That is verified on every run by testing the mean coordinate against the extent, because a swapped axis order produces a plausible-looking map of entirely the wrong place rather than an error.
